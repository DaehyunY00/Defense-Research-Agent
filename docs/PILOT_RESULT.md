## 2. 구현 결과

### 독립 평가

- `PolicyRelevanceEvaluator`: 정책 관련성, 시의성, 정책 영향
- `NoveltyEvaluator`: 기존 연구 대비 신규성
- `EvidenceFeasibilityEvaluator`: 공개 근거 충분성, 수행 가능성
- `OutputFitEvaluator`: 산출물 적합성
- 평가 입력에 다른 평가 결과가 없으며 후보/평가기 작업은 병렬 실행 가능
- 평가별 제한 재시도, 시도 횟수, 부분 실패, 누락 기준 기록
- Pydantic `EvaluationResult` 검증과 허용 근거 ID 검사
- 무근거 60점 초과 상한과 기존 제목 직접 중복 신규성 20점 상한

### 랭킹과 다양성

- 일곱 기준 가중합을 `configs/scoring.json`으로 설정
- 직접 중복, 공식자료 부족, 과도한 범위, 단순 해외사례, 근거·confidence·기준 누락 감점
- 정책 분야, 국가, 산출물, 단기/구조적 연구 반복 조정
- 원점수, 감점 후 점수, 다양성 조정 후 점수와 사유 보존
- 동점은 `candidate_id` 오름차순으로 결정
- 다양성 조정 비활성화 지원

### 인간 승인

- 결정: `approve`, `approve_with_edits`, `hold`, `reject`
- `review_history.jsonl` append-only 저장, 파일 잠금·`fsync`·연속 sequence 검증
- 같은 `run_id`의 이전 랭킹과 이력으로 CLI 재개
- 미검토·보류 후보가 있으면 `awaiting_review`
- 승인 또는 수정승인 후보만 주제기획 카드 생성
- 실제 승인 전 `topic_planning_cards.json` 미생성

### 평가 하네스

- 데이터 파싱, 내부 검색, 주제 생성, 평가, 오케스트레이션, 전문가 출력 지표
- 계산 불가능한 지표의 명시적 `unavailable`
- 기준 연도 이하 입력/이후 목표의 시점 분할과 미래 누출 검사
- 상위 5개 근거·점수 내역 Markdown과 전문가 입력 CSV
- 부분 실패를 숨기지 않는 실패 사례 목록

## 7. 변경 검토와 보안 검토

현재 디렉터리는 Git worktree가 아니므로 `git diff`와 미커밋 상태를 검토할 수 없다.
대신 전체 `src/`, `tests/`, `configs/`, `docs/`, README를 정적 검사하고 새 산출물을
Pydantic으로 다시 읽었다. Git 이력이 필요한 변경 추적은 저장소 초기화 또는 올바른
worktree 연결 후 다시 수행해야 한다.

보안 검토 결과:

- 기본 오프라인 검증에서 네트워크 Provider, 외부 모델 API와 운영 DB를 호출하지 않음
- 선택적 Anthropic·GCP adapter가 있지만 자격증명이 없으면 조립하거나 호출하지 않음
- 비밀정보·API 키를 생성하거나 저장소에 기록하지 않음
- 외부 fixture 콘텐츠는 `untrusted`로 보존하고 그 지시문을 실행하지 않음
- 모델 평가 출력은 Pydantic 및 허용 근거 ID로 검증
- 점수·감점·정렬·분기·승인 상태는 Python 코드가 결정
- `run_id` 경로 traversal 차단
- 검토 터미널 제어문자, Markdown HTML, CSV 수식 주입 완화
- 승인 이력은 기존 줄을 덮어쓰지 않고 추가만 수행
- Firestore 상태 전이·검토 append는 transaction으로 경쟁 쓰기를 검증
- 기본 테스트에 네트워크 호출 없음

잔여 보안 위험:

- append-only JSONL은 로컬 파일 권한을 가진 사용자의 사후 변조를 암호학적으로
  탐지하지 못한다.
- 별도 검토 UI는 없고 운영 API 인증은 Cloud Run IAM에 의존하므로 세부 연구자 역할
  권한은 추가 설계가 필요하다.
- 로컬 파일 잠금과 Firestore transaction은 경쟁 쓰기를 막지만 분산 승인 요청의
  자동 재시도·사용자 충돌 해결 UX는 없다.
- 실제 Web/LLM 운영 시 프롬프트 인젝션 회귀, provider 정책, rate limit, 비용과 감사
  로그를 지속 검토해야 한다.


수행하지 않았고 모든 새 실행 결과는 `artifacts/`에만 기록했다.

2단계 첫 작업은 **전문가 골든셋과 페이지 근거 청킹을 함께 설계하는 것**이다.
현재 `unavailable` 지표를 실제 품질 판정으로 바꾸고, 후보 근거를 PDF 페이지까지
검증하려면 두 작업이 선행돼야 한다.
