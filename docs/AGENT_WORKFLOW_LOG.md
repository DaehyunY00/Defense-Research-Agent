# 병렬 에이전트 개발 기록

codex를 구현자로, Claude를 교차 검증자로 쓰는 개발 루프를 도입하면서 발생한 문제와
내린 결정을 기록한다. 사용법은 [scripts/README.md](../scripts/README.md), 아키텍처
결정은 [DECISIONS.md](./DECISIONS.md), 작업 backlog는
[IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md)를 참조한다.

이 문서는 "무엇을 했는가"가 아니라 **"무엇이 틀렸고 왜 그렇게 고쳤는가"**를 남긴다.
같은 함정을 다시 밟지 않기 위한 기록이다.

## 1. 구조

```text
[직렬] 계약 확정 (Protocol/ABC + 도메인 모델)  ← 사람 + Claude
   ↓
[검증] 레인 하나로 계약이 구현에 견디는지 확인
   ↓
[직렬] base 확정
   ↓
[병렬] 레인별 구현                              ← codex
   ↓
[검증] G0 결정적 게이트 → Claude 교차 리뷰       ← 레인별 병렬
   ↓
[직렬] 통합, 배럴 재노출, 체크박스 확정          ← 사람
```

게이트는 계층으로 쌓는다. 비싼 리뷰 앞에 싸구려 결정적 게이트를 둔다.

```text
G0  uv run pytest / mypy / ruff       무료·결정적. 실패 시 Claude를 호출하지 않는다
G2  Claude 교차 리뷰                   진짜 게이트
G3  사람                               도메인 판단·체크박스 확정
```

### 왜 교차 모델인가

`gpt-5.6-sol`과 `opus-5`는 오류 상관관계가 낮다. 같은 모델의 자기 리뷰는 자기 가정을
그대로 승인한다. 여기에 컨텍스트 분리가 더해진다 — 리뷰어는 구현자의 추론 과정을 보지
못하고 결과 diff만 보므로 "왜 이렇게 했는지"에 설득당하지 않는다.

리뷰어 프롬프트가 구현자의 자기 보고(`RESULT.md`, 커밋 메시지, 문서 체크 표기)를 근거로
삼지 못하도록 명시한다. 이게 없으면 교차 검증의 의미가 사라진다.

## 2. 워크플로 결함과 수정

실행 중에 발견해 고친 것들이다. 전부 레인 하나를 먼저 돌렸기 때문에 드러났고,
레인 4개를 동시에 띄웠다면 각각 4번씩 터졌을 문제다.

### 2.1 `--allowedTools`가 프롬프트를 삼킨다

`claude -p ... --allowedTools "Read" "Grep" "<프롬프트>"` 형태로 호출하면 가변 인자인
`--allowedTools`가 프롬프트를 옵션 값으로 흡수하고
`Input must be provided either through stdin or as a prompt argument`로 죽는다.

**수정**: 모든 프롬프트를 stdin으로 넘긴다.

### 2.2 macOS 기본 bash 3.2 + `set -u`

빈 배열 전개 `"${ARGS[@]}"`가 `unbound variable`로 실패한다. macOS 기본 bash는
3.2.57이다.

**수정**: `${ARGS[@]+"${ARGS[@]}"}`.

### 2.3 codex가 worktree에서 커밋하지 못한다

`git worktree`의 `.git`은 파일이고 실제 git dir는 상위 저장소 안에 있다.
`codex exec -s workspace-write`는 worktree만 쓰기 허용하므로 `index.lock`을 만들지
못한다. 이 저장소는 Google Drive 경로에 있어 더 확실히 막힌다.

P1.1 레인에서 실제로 발생했다. 구현과 검증은 전부 끝났는데 커밋만 되지 않았다.
codex가 조용히 실패하지 않고 원인을 정확히 진단해 보고한 점은 좋은 신호였다.

**수정**: `codex exec --add-dir "$(git rev-parse --git-common-dir)"`.

### 2.4 리뷰어가 섹션을 못 찾아도 오류를 내지 않는다

첫 캘리브레이션에서 `SECTION=P1.1`을 줬는데 대상 worktree의 계획 문서는 구버전이라
`P1.1` 섹션이 아예 없었다. 리뷰어는 오류를 내는 대신 **조용히 다른 섹션으로 대체 판정**
했다. 결과물이 그럴듯해서 알아채기 어렵다.

여기서 파생된 운영 요구사항: **base 브랜치는 최신 `docs/`를 포함해야 한다.** 루브릭이
곧 `AGENTS.md`와 `IMPLEMENTATION_PLAN.md`이므로, base의 docs가 낡으면 구현자와
리뷰어가 둘 다 구버전 계획을 기준으로 판단한다.

**수정**: `lane-review.sh`가 사전에 grep으로 섹션 존재를 확인해 조기 차단하고,
리뷰어 프롬프트도 `SECTION_NOT_FOUND`로 즉시 중단하도록 지시한다.

### 2.5 레인 경계 규칙이 Definition of Done과 충돌했다

프롬프트가 "작업 범위는 이 파일들뿐"이라고 못 박았는데 DoD는 "관련 documentation
업데이트"를 요구한다. P1.1 레인에서 codex는 명시된 경계를 지키고 문서를 갱신하지
않았다 — 옳은 행동이다. 그 결과 계획 문서가 구현과 모순되는 서술을 단언한 채 남았다.

리뷰어의 파급 분석이 정확했다. 해당 항목이 P1.7 착수의 선행 조건으로 지정돼 있으므로,
다음 작업자가 완료된 작업을 미완으로 읽고 P1.7을 보류하거나 중복 구현한다.

**수정**: 프롬프트 템플릿에 예외를 명시한다 — "해당 레인의 계획 섹션은 **반드시**
갱신한다. 다른 섹션은 여전히 금지." 충족하지 않은 항목을 체크하지 않는다는 조건도 함께.

### 2.6 리뷰어에게 테스트를 실행시키지 않는다

샌드박스에서 거부되기도 하고, G0가 이미 돌았으므로 중복이다.

**수정**: `--allowedTools`에서 `Bash(uv run:*)`를 빼고, 프롬프트에 G0 로그 경로를 준다.

### 2.7 `--git-common-dir` 상대 경로

2.3의 수정을 적용했는데도 레인 4개가 **전부 다시 커밋에 실패했다.** 임시 실행
스크립트가 메인 저장소에서 `git rev-parse --git-common-dir` 를 불렀고, 그 경우 반환값이
절대 경로가 아니라 `.git` 이다. 이 상대 경로가 codex의 CWD(worktree) 기준으로 해석되어
`worktree/.git` — 즉 **파일**을 가리켰다.

worktree에서 부르면 절대 경로가 나온다. `lane-run.sh` 는 원래 올바랐고 임시 스크립트만
틀렸다.

**수정**: `lib.sh` 에 `git_common_dir()` 헬퍼를 만들어 절대 경로를 강제하고 두 스크립트가
이를 쓰게 했다. 다음 라운드에서 codex가 스스로 커밋하는 것을 확인했다.

### 2.8 레인 실행 산출물이 추적됐다

`git add -A`에 `G0.log`, `REVIEW.md`, `RESULT.md`, `codex.jsonl`이 딸려 들어갔다.

**수정**: `.gitignore`에 추가.

## 3. 교차 리뷰가 잡은 실질 결함

전부 사람이 코드와 `DATA_QUALITY_REPORT.md`로 재확인했다.

### 3.1 통과하지만 실제 경로를 검증하지 않는 테스트

리뷰어의 주된 값은 여기 있었다.

- `search/chunking.py`의 `exceeds_limit` 분기가 어떤 테스트에서도 참이 되지 않았다.
  유일한 크기 테스트가 `max_characters=10`, 페이지 4/4/20이라 `4+2+4=10 > 10`이
  False가 되어 사후 검사로만 분할됐다. 기본값 4,000자와 실제 페이지 길이에서는 이
  분기가 주 경로다.
- `crosses_page_gap` 분기도 미발화. 빈 페이지 테스트에서 `emit_pending()` 후
  `pending`이 비어 이 분기를 타지 않았다.

**교훈**: 분기 커버리지는 테스트 개수가 아니라 **어떤 분기가 실제로 참이 되는지**로
판정해야 한다. 리뷰어 루브릭에 이 문장을 명시적으로 넣었다.

### 3.2 fake가 실제 코퍼스를 과대 대표

품질 게이트 fake가 `control_character_count=0`을 하드코딩했다. DQ-03은 370개 중
192개에 제어문자가 있다고 기록한다(국방논단 100/100, 국방정책연구 59/59). 즉 fixture가
코퍼스의 거의 어느 문서도 대표하지 않았다.

리뷰어가 독립적으로 `data/`를 측정해 국방논단 1.7~5.0% 대역을 찾아냈고, 이후 사람이
`scripts/measure_quality_thresholds.py`로 측정한 값과 일치했다(2024_김영곤
727/14,518 = 5.01%).

**교훈**: fixture가 실제 데이터로 재현 불가능한 동작을 대표하고 있지 않은지 확인하는
항목을 루브릭에 넣었다. 원본 데이터 스키마를 직접 확인해서 판정하도록 지시한다.

### 3.3 테스트가 완화된 임계값을 쓰면 배포 동작을 검증하지 못한다

품질 게이트 테스트가 운영 기본값(0.01)의 5배 느슨한 사본(0.05)을 썼다.

**수정**: 테스트가 운영 기본값을 그대로 쓰도록 바꾸고, fixture가 실측 대역 안에 있는지
검사하는 테스트를 추가했다.

### 3.4 계약이 기존 모델보다 표현력이 낮았다

첫 metadata 계약의 `ExtractedMetadataValue.normalized`가 `str | None` 단일 스칼라라
저자 N명을 담을 수 없었다. 기존 `ResearchPublication.authors`는 `list[Label]`이므로
**퇴행**이었다. `DATA_QUALITY_REPORT.md`는 `authors[]`에 name/role/affiliation/
email/is_primary/raw_text/evidence_page/confidence를 요구한다.

같은 계약이 파일명 연도·processed date·published date를 분리 보존하지 못했고,
`DatePrecision`에 `season`이 없어 국방정책연구 59개 전체의 `2024년 여름(40-2)` 표기를
표현할 수 없었다.

**수정**: `ExtractedAuthor`, `PublicationDates`, `MetadataEvidenceSource`,
`DatePrecision.SEASON` 도입.

### 3.5 문서화만 하고 강제하지 않은 규칙

"표지 근거 우선"이 docstring과 `source_path` 파라미터로만 존재했다. 강제하는 validator도
없었고, 테스트는 `source_path`를 **한 번도 전달하지 않았다.**

**수정**: `MetadataEvidenceSource`로 근거 출처를 타입화하고 우선순위를 정의했다.
문서 기반 근거는 `page_number`를 요구하고 파일명 근거는 금지한다. fake extractor가
`source_path`를 실제로 사용하고, DQ-04의 불완전 자모 파일명에서 표지가 이기는지
테스트한다.

## 4. 결정 사항

### 4.1 계약 설계

| 결정 | 근거 |
|---|---|
| `ExtractionProvenance`에 타임스탬프 없음 | 파생 산출물은 같은 원본·같은 버전에서 byte 재현이 가능해야 한다. wall-clock 필드가 그걸 깬다. 실행 시각은 `artifacts/` 로그 소관 |
| 파서가 예상 실패를 raise하지 않고 반환 | 부분 추출된 문서가 뽑아낸 페이지를 잃지 않게 한다. 프로그래밍 오류만 예외로 전파 |
| 품질 게이트 `measure`/`evaluate` 분리 | threshold만 바뀌었을 때 corpus 재파싱 없이 저장된 measurements로 재판정 |
| `embedding_model_id` 명명 | Pydantic이 `model_` 접두사를 protected namespace로 잡는다 |
| 배럴 재노출은 통합 단계에서 일괄 처리 | `domain/__init__.py`는 264줄 알파벳순 배럴이라 레인마다 export를 추가하면 확정적으로 충돌 |
| provenance 변경도 chunk 경계 | P1.4 페이지 단위 OCR fallback이 한 문서 안에 서로 다른 추출기 산출물을 섞는다 |
| `chunk_id` v2에 parser 식별자 포함 | parser version만 바뀌면 `provenance`와 `chunk_id`만 바뀌고 text·checksum·page span은 유지된다 |
| 인용 단위는 페이지 범위가 아니라 단일 페이지 | 성공 기준이 인용의 문서·페이지 역추적 100%다. `PublicationPageSpan`으로 offset을 보존 |

### 4.2 품질 임계값

측정으로 확정했다. 상세는 [DECISIONS.md](./DECISIONS.md)의 ADR-010.

핵심은 **코드포인트별 "문서 수"가 "총 발생 수"와 다른 그림을 준다**는 것이었다.
총 발생 수 1위는 `U+0005`(66,662)지만 이는 단일 문서에만 있다. 실제로 넓게 퍼진 것은
`U+0001`로 163개 문서에 나타난다.

`U+0001`을 공백으로 치환한 뒤 측정한다. 치환하지 않고 `0.01`을 적용하면 86개(23.2%)가
제외되고 그중 78개가 국방논단이다. 치환 후에는 정확히 1개만 제외된다.

한글 비율은 도메인 판단이 필요할 줄 알았으나 측정으로 해소됐다. 국방정책연구 최저값이
0.338이라 `min_korean_ratio=0.1`은 59개 전체에 존재하는 영문 Abstract 구간과 무관하게
안전하다.

### 4.3 base 확정 절차

레인 4개를 바로 띄우지 않고 **P1.1 레인 하나를 먼저 돌려 계약을 검증**했다.

결과: `PublicationPage`에 필수 필드를 추가하는 변경이 parser/metadata/quality 계약
셋을 관통했는데 **공개 시그니처 변경이 0건**이었다. `ParseResult`가 이미 run 단위
provenance를 갖고 있던 설계가 그대로 맞아떨어졌다. 되돌리기 비용이 높다고 표시했던
"파서의 예상 실패 반환 방식"도 마찰 없이 통과했다.

이 판단이 맞았다는 증거는 2.3과 2.5의 워크플로 결함이다. 둘 다 모든 레인에 해당하는
구조적 문제였고, 4개를 동시에 띄웠다면 각각 4번씩 터졌을 것이다.

base는 `base/document-intelligence` 태그로 고정한다.

### 4.4 레인 A 범위 축소

P1.3의 PDF 본문 직접 추출을 제외하고 JSON page adapter만 맡겼다. PDF 파싱 라이브러리가
의존성에 없고 선택이 라이선스 결정이기 때문이다.

`data/metadata/*.json`에 이미 `page_texts`가 있으므로 의존성 없이도 chunking·quality·
metadata가 실제 페이지 위에서 동작한다. PDF 재추출은 품질 개선이지 파이프라인 전제가
아니다.

## 5. 남은 결정

| 항목 | 상태 |
|---|---|
| PDF 파싱 라이브러리 선택 | **pypdfium2 로 확정.** 아래 참조 |
| `section_title` 유지 여부 | 유지하기로 결정. 단 파서가 heading을 채우기 전까지 항상 `None`이고 `changes_section` 경계는 실제 코퍼스에서 발화하지 않는다. P1.3 파서 heading 추출이 전제 |

| `U+0007` 보유 29개 문서 | 치환 대상이 아니므로 `warning`으로 색인된다. 공백 대체라는 근거가 확인되면 치환 목록에 추가 가능 |

### PDF 라이브러리 비교

코퍼스가 370개이므로 **속도는 의미 있는 축이 아니다.** 어떤 라이브러리든 전체 추출이
몇 분 안에 끝난다. 최적화할 축은 추출 정확도다.

| 라이브러리 | 라이선스 | 텍스트 정확도 | 표·레이아웃 | 비고 |
|---|---|---|---|---|
| PyMuPDF | **AGPL-3.0** | 최상 | 좋음 | 네트워크 조항이 Cloud Run API 배포에 걸린다 |
| pypdfium2 | BSD-3 / Apache-2.0 | 최상급 | 보통 | Google PDFium 바인딩 |
| pdfplumber | MIT | 좋음 | 최상 | `pdfminer.six` 의존, 느림 |
| pypdf | BSD-3 | 보통 | 약함 | 순수 Python, 의존성 없음 |

AGPL-3.0 §13은 사용자가 네트워크로 상호작용하면 전체 저작물의 대응 소스를 제공하도록
요구한다. 이 저장소는 `deploy/gcp-app/`에 Cloud Run API를 포함하므로 정면으로 걸린다.

**결정: pypdfium2.** "가장 빠르고 정확한 것"이라는 요구를 AGPL 없이 충족한다. 아직
ADR로 기록하지 않았고 P1.3 나머지도 구현하지 않았다.

이 결정은 되돌릴 수 없는 것이 아니다. `DocumentParser` 계약이 `ParserCapability.TABLES`
와 복수 adapter를 지원하므로, 하나로 시작하고 품질 게이트가 문제를 보여주면 두 번째
adapter를 추가하면 된다. 측정 없이 미리 고르지 않는다.

## 6. 교훈

- **인터페이스를 직렬로 먼저 고정한다.** 병렬 에이전트가 실패하는 원인은 merge 충돌이
  아니라 각자 다른 인터페이스를 발명하는 것이다. 코드는 깨끗하게 merge되고 설계만 두
  개가 된다.
- **레인 하나를 먼저 돌린다.** 계약의 약점과 워크플로 결함은 첫 구현자가 가장 잘
  드러낸다. 여기서 나온 문제는 1번만 고치면 되고, 병렬로 띄운 뒤 나오면 N번 고쳐야 한다.
- **"대략적인 구현 후 리뷰"는 권하지 않는다.** 리뷰어는 구현자가 놓친 것은 잘 잡지만
  일부러 건너뛴 것은 잘 못 잡는다. 없는 테스트, 안 만든 실패 경로는 diff에 흔적이 없다.
  구현자에게 DoD를 완전히 만족시키게 하고 리뷰어는 "정말 만족했는지" 검증하게 한다.
- **리뷰어에게 루브릭을 준다.** 없으면 스타일 지적으로 흐른다. 이 프로젝트는 `AGENTS.md`
  절대 규칙 7개와 Definition of Done 17개 항목이라는 기계적으로 검증 가능한 루브릭을
  이미 갖고 있었다.
- **되먹임에 `codex exec resume`을 쓴다.** 새 세션에 지적사항을 던지면 자기 코드를 처음
  보는 상태로 다시 읽어야 한다. resume은 구현 당시 컨텍스트를 유지한 채 고친다.
- **"반박도 유효한 응답"이라고 명시한다.** 없으면 codex가 틀린 지적까지 수용해 멀쩡한
  코드를 망친다. 리뷰어의 오탐률은 0이 아니다.
- **라운드 상한을 둔다.** 3라운드째에도 남는 지적은 대개 모델 간 의견 충돌이거나 사양
  자체가 애매한 경우라 사람이 판정하는 편이 빠르다.
- **에이전트 보고를 그대로 믿지 않는다.** 구현자의 완료 보고도, 리뷰어의 지적도 코드로
  재확인한다. 이번 기록의 모든 결함은 사람이 코드와 원본 데이터로 검증한 것이다.
- **체크박스는 사람이 확정한다.** `IMPLEMENTATION_PLAN.md`의 backlog 운영 규칙이다.

## 8. 추가로 확인된 코퍼스 사실 — 국방논단과 Brief에는 발행일이 없다

P1.5 작업 중 발행일 추출 규칙을 정하면서 실측으로 확인했다.

`data/metadata/*.json` 의 `page_texts` 기준으로 발행일을 확정할 수 있는 문서:

| 유형 | 확정 가능 | 비고 |
|---|---|---|
| 국방정책연구 | 61/61 (100%) | 간기에 발행 표기 |
| 연구보고서 | 35/38 (92%) | 대부분 간기줄 |
| 국방논단 | **0/100** | 추출 텍스트에 발행일 없음 |
| Brief | **0/173** | 동일 |

국방논단 54개와 Brief 9개에 `YYYY년 M월 D일` 형태의 일 단위 날짜가 나타나지만 전부
산문 날짜다. 확인한 예:

- `한국연구재단의 국내 학술지 평가에서 2009년 1월 1일부로 등재학술지로` — 학술지 등재일
- `2023년 10월 17일, 윤석열 대통령이 ADEX 2023의 개막` — 행사일
- `2020년 6월 4일에「국방정보화업무훈령」이 개정되` — 법령 개정일

`국방정책연구는 한국국방연구원에서 연 4회 발행하는 계간지로서 2008년…` 처럼 발행 마커를
포함하는 줄도 저널 소개 문구이지 해당 호의 발행일이 아니다.

### 이것이 뜻하는 것

- 코퍼스의 73%(273/372)는 `published_at` 을 확정할 수 없다. `filename_year` 가 유일한
  연도 신호다. 시계열 분석과 temporal backtest 는 이 사실을 전제로 설계해야 한다.
- `DATA_QUALITY_REPORT.md:151` 이 국방논단의 발행 표기 예로 든 `2024년 11월 4일` 은
  현재 JSON 추출 텍스트에서는 발행일로 식별되지 않는다. PDF 간기에는 있으나 JSON
  추출이 놓쳤을 가능성이 있다. 레인 E 가 추가한 PDF 직접 추출로 회수되는지 확인할 가치가
  있다. `PageTextSelection` 이 두 소스를 모두 보존하므로 비교 가능하다.

### 측정 방법론에서 배운 것

처음에 "발행 마커가 있는 줄"을 단순 정규식으로 세어 국방논단 36%, Brief 5% 를 목표로
제시했는데 **틀린 수치였다.** 마커 단어가 저널 소개 문구와 다른 발간물 언급에도 나타나기
때문이다. 그 수치를 그대로 목표로 밀었다면 구현을 잘못된 방향으로 끌고 갔을 것이다.

되먹임에 "이 목표 수치는 근사 정규식 기준이므로 정확한 상한이 아니다. 더 정확한 판정으로
목표보다 높은 확정률이 나오면 근거를 적어라"는 단서를 달아 둔 것이 도움이 됐다.
구현이 목표보다 낮은 값(0%)을 냈고, 그 쪽이 사실이었다.

**교훈**: 사람이 만든 측정도 검증 대상이다. 에이전트에게 목표 수치를 줄 때는 그 수치의
도출 방법과 신뢰 한계를 함께 준다.
