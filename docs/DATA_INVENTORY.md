# defense-research-agent 데이터 인벤토리

## 1. 조사 범위와 기준

- 조사 시점: 2026-07-27 (Asia/Seoul)
- 조사 범위: 저장소 전체와 `data/` 이하 모든 디렉터리 및 파일
- 조사 방법: 재귀 파일 열거, MIME/확장자/크기 집계, 모든 JSON의 UTF-8 디코딩 및 JSON 파싱, 모든 PDF의 헤더와 `pdfinfo` 검사, SHA-256 기반 동일 파일 검사, 대표 PDF 렌더링 및 텍스트 추출 비교
- 안전 원칙: `data/`의 원본 파일을 수정·삭제·이동하지 않았다. 외부 API와 운영 DB에는 연결하지 않았다.
- 지침 파일: 조사 시작 시점에 이 저장소 안에는 `AGENTS.md`와 `docs/`가 없었다. 상위의 다른 프로젝트에 있는 `AGENTS.md`는 이 저장소의 지침으로 간주하지 않았다.

이 문서에서 사용하는 수량의 의미는 다음과 같다.

- **전체 파일**: `.DS_Store`까지 포함한 실제 파일 수
- **문서 JSON 레코드**: `metadata`, `full_text`, `page_texts` 스키마를 가진 JSON 수
- **고유 연결 문서**: `(category, metadata.filename)`을 NFC 정규화한 뒤 하나의 PDF에 연결되는 고유 문서 수

## 2. 저장소 구조

조사 시작 시 저장소에는 애플리케이션 코드나 설정 파일이 없고 `data/`만 있었다.

```text
defense-research-agent/
└── data/
    ├── .DS_Store
    ├── Brief/
    ├── metadata/
    ├── 국방논단/
    │   └── .DS_Store
    ├── 국방정책연구/
    │   └── .DS_Store
    └── 연구보고서/
```

실제 macOS 파일명에서는 세 한글 디렉터리와 일부 파일명이 분해형 유니코드로 저장돼 있다. 위 트리는 읽기 편하도록 NFC 표기로 표시했다.

- PDF 371개는 모두 `%PDF-` 헤더를 가지며 `pdfinfo`로 열렸다.

## 5. 파일명 규칙

### 5.1 PDF

PDF 371개 모두 다음의 최소 패턴과 일치한다.

```text
YYYY_<대표저자>_<제목>.pdf
```

- `YYYY`: 4자리 연도
- `<대표저자>`: 첫 번째와 두 번째 밑줄 사이의 값
- `<제목>`: 두 번째 밑줄 이후의 나머지 전체

대표저자 구간 371개는 모두 한글 또는 영문 이름으로 읽을 수 있었고 공백은 없었다. 다만 제목 구간에는 공백, 괄호, 아포스트로피, 물결표, 추가 밑줄이 일부 존재하므로 단순히 모든 밑줄을 기준으로 나누면 안 된다.

연도는 정규화된 발행일 필드가 아니라 파일명 선두 값이다. 예를 들어 일부 `Brief`는 파일명 연도와 제목 속 사업연도가 다르고, 일부 `국방정책연구`는 파일명 `2025`이지만 본문 이슈 표기는 `2024년 겨울`이다.

### 5.2 문서 JSON

문서 JSON 372개도 모두 다음 최소 패턴과 일치한다.

```text
YYYY_<대표저자>_<정제된 제목>.json
```

그러나 JSON 파일명은 PDF 파일명의 괄호, `&`, 가운데점, 공백 등을 밑줄로 치환한 경우가 있다. JSON 파일명 stem과 `metadata.filename`의 PDF stem이 정확히 같은 것은 322/372개뿐이다. 따라서 PDF 연결 키로 JSON 파일명을 사용하면 안 되고, 반드시 JSON 내부의 `metadata.category`와 `metadata.filename`을 사용해야 한다.

### 5.3 유니코드와 길이

- PDF 파일명 371개 중 164개, JSON 파일명 373개 중 165개는 NFC가 아니다.
- PDF 파일명 37개는 UTF-8 기준 240바이트 이상이고 3개는 255바이트다.
- 문서 JSON 파일명 39개는 240바이트 이상이고 8개는 255바이트다.
- PDF와 JSON 각각 11개 파일명은 제목 끝이 완성되지 않은 한글 자모로 끝난다.

이는 파일명 기반 제목이 잘렸을 가능성과 운영체제 간 매칭 실패 위험을 뜻한다. 원본 이름을 바꾸지 말고, 파생 인덱스에서 NFC 정규화 값과 원본 값을 함께 보존해야 한다.

## 6. 문서 JSON 실제 스키마

문서별 JSON 372개는 모두 동일한 최상위 스키마를 가진다.

```json
{
  "metadata": {
    "filename": "string",
    "path": "string",
    "category": "string",
    "num_pages": 4,
    "file_size_mb": 5.75,
    "processed_date": "2026-02-02T23:30:06.937817",
    "total_chars": 29,
    "avg_chars_per_page": 7
  },
  "full_text": "string",
  "page_texts": [
    {
      "page": 1,
      "text": "string",
      "char_count": 21
    }
  ]
}
```

필드 해석:

| 필드 | 형식 | 관찰된 의미 |
|---|---|---|
| `metadata.filename` | string | 원본 PDF 파일명 |
| `metadata.path` | string | PDF를 처리했을 당시의 절대 경로 |
| `metadata.category` | string | `Brief`, `국방논단`, `국방정책연구`, `연구보고서` 중 하나 |
| `metadata.num_pages` | integer | PDF 페이지 수 |
| `metadata.file_size_mb` | float | MiB 단위로 소수 둘째 자리까지 반올림한 크기 |
| `metadata.processed_date` | string | 문서 추출 처리 시각. 발행일이 아님 |
| `metadata.total_chars` | integer | 추출 파이프라인이 기록한 문자 수 |
| `metadata.avg_chars_per_page` | integer | `total_chars / num_pages`의 반올림 값 |
| `full_text` | string | 페이지별 추출 텍스트를 합친 값 |
| `page_texts[].page` | integer | 1부터 시작하는 연속 페이지 번호 |
| `page_texts[].text` | string | 해당 페이지의 추출 텍스트 |
| `page_texts[].char_count` | integer | 해당 `text`의 실제 문자열 길이 |

명시적으로 존재하지 않는 주요 필드는 `title`, `author`/`authors`, `abstract`, `publication_date`, `year`, `doi`, `url`, `keywords`다. 이 값 중 일부는 PDF 또는 `full_text` 안에만 비구조화 상태로 존재한다.

`metadata.total_chars`는 모든 고유 레코드에서 실제 `len(full_text)`보다 2~12자 크다. 반면 각 페이지의 `char_count`는 실제 페이지 문자열 길이와 일치하고, `avg_chars_per_page`는 기록된 `total_chars`를 기준으로 한 반올림 값과 일치한다.

### 6.1 `pdf_index.json` 스키마

`data/metadata/pdf_index.json`은 문서 레코드가 아니라 처리 결과 집계다.

```json
{
  "total_documents": 370,
  "failed_documents": 0,
  "processed_date": "2026-02-02T23:30:18.949037",
  "category_stats": {
    "국방논단": 100,
    "국방정책연구": 59,
    "Brief": 173,
    "연구보고서": 38
  },
  "documents": ["metadata 객체 370개"],
  "failed_files": []
}
```

이 인덱스의 370개는 현재 확인된 고유 연결 문서 수와 일치한다. 다만 현재 `data/`에는 인덱스에 없는 PDF 1개와 인덱스 문서 목록만으로는 드러나지 않는 중복 문서 JSON 2개가 있으므로, 이 파일만으로 현재 디렉터리 상태를 판단하면 안 된다.

## 7. 유형별 실제 콘텐츠 구조

대표 파일은 각 유형의 추출 텍스트 길이 중앙값 부근에서 선택해 JSON, 실제 PDF 텍스트, 렌더링된 첫 페이지를 함께 확인했다.

| 유형 | 고유 문서 | 페이지 수 최소/중앙/최대 | `full_text` 길이 최소/중앙/최대 | 실제 구조와 식별 신호 |
|---|---:|---:|---:|---|
| KIDA Brief (`Brief`) | 173 | 4 / 4 / 5 | 16 / 4,713 / 6,563 | 표지의 `KIDA Brief`, 호수, 제목, 저자·센터, `배경과 목적`, `수행 결과`, 본문 |
| 국방논단 | 100 | 8 / 12 / 20 | 7,560 / 13,874.5 / 24,932 | `국방논단`, 제호와 발행일, 발행처·발행인·편집인, 제목, 복수 저자·소속·이메일, 요약 성격의 도입부, 본문 |
| 국방정책연구 | 59 | 18 / 31 / 57 | 21,689 / 35,522 / 66,466 | 계절·권호·통권·쪽수, DOI, ISSN, 제목, 저자, 목차, 영문 `Abstract`, `Keywords`, 본문, 참고문헌 |
| 연구보고서 | 38 | 3 / 21.5 / 521 | 45 / 15,284 / 719,268 | 보고서 번호, ISBN, 제목, 복수 저자, `YYYY. M.`, 고지문, 머리말·목차·본문·부록 등. 일부 파일은 짧은 공개본 또는 추출 실패 |

따라서 네 자료 유형은 다음 우선순위로 안정적으로 구분할 수 있다.

1. `metadata.category`
2. PDF의 상위 폴더
3. 유형별 표지·본문 식별 신호

파일명 제목이나 본문 문자열만으로 유형을 추론할 필요는 없다.

## 8. PDF와 메타데이터 연결 현황

NFC 정규화한 `(metadata.category, metadata.filename)`을 현재 PDF의 `(상위 폴더명, 파일명)`과 비교한 결과:

- 문서 JSON 레코드 372개 모두 어떤 PDF에는 연결된다.
- 중복 대상을 제거하면 고유하게 연결되는 PDF는 370개다.
- PDF 371개 중 1개는 연결되는 문서 JSON이 없다.
- `pdf_index.json`의 `documents`도 370개다.
- 현재 PDF 전체 페이지는 7,170쪽이고, 메타데이터가 있는 고유 370개 PDF는 7,158쪽이다. 차이 12쪽은 메타데이터가 없는 국방논단 PDF다.
- 연결된 PDF의 실제 페이지 수는 모든 문서 JSON의 `metadata.num_pages`와 일치했다.

`metadata.path` 372개는 모두 현재 저장소가 아니라 `Desktop/KIDA_RAG_System/Data/...` 아래를 가리키는 절대 경로다. 현재 환경에서 경로가 존재하더라도 저장소 이동과 다른 사용자 환경에서 재현할 수 없으므로 연결에는 사용하지 않아야 한다.

## 9. 대표 검증에서 확인한 내용

- 정상 `Brief`, `국방논단`, `국방정책연구`, `연구보고서` 각 1개를 렌더링했으며 표지의 제목·저자·발행 정보와 JSON 추출 텍스트가 대응했다.
- `국방정책연구` 대표 파일은 PDF에 DOI, 영문 초록, 키워드가 있지만 JSON에는 이들을 위한 별도 필드가 없었다.
- 텍스트가 16자인 `Brief`의 2쪽을 렌더링하니 실제 한글 본문이 존재했다. 즉 원본 누락이 아니라 텍스트 추출 실패다.
- 텍스트가 45자인 `연구보고서`도 표지에 제목·복수 저자·발행월이 존재했지만 JSON에는 고지문만 추출됐다.
- 제어문자가 매우 많은 521쪽 `연구보고서`의 표지는 시각적으로 정상이다. PDF 손상보다는 폰트/문자 매핑에 따른 추출 손상으로 판단된다.
